На странице 179 пример двух покупок по 1000 и 2000 с разных складов даёт себестоимость продажи 1500. Это подтверждает смысл нашей проверки BU13: количество ограничено складом отгрузки, стоимостная средняя определяется по номенклатуре по компании. Конкретные имена регистра и признаки учёта из раздела решения не становятся обязательным архитектурным шаблоном.

На странице 182 в перечне и таблице видов расчёта база годовой премии указана как ТРФ/ТРН/КМД, а в строке формулы — ОКЛ + ТРН + ТРФ. Это внутреннее расхождение: появился отсутствующий в перечне ОКЛ и пропал КМД. Копировать такую строку в формальные привязки без проверки полной конфигурации нельзя. Арифметический смысл базы нужно выводить из условия о всех начислениях прошлого года и затем сверять с решением на диске.

## Как использовать найденное

Для текущего пакета книга подтверждает отдельные смыслы и помогает создавать отрицательные контрольные примеры проверяющего. Она не закрывает вопросы о направлении сортировки аналогов, оценке сборки и частичной премии при командировке. Полный эталон для этого пакета пока не подтверждён.

Если следующим пакетом выбрать **именно комплект из книги**, ему нужен отдельный ID, чистая постановка только из подразделов «Условие задачи» и набор приёмки по его условиям. Разделы «Решение» останутся у куратора для калибровки. Это позволит проверить судью на авторском решении при наличии соответствующих исходников с диска/официальной поставки, не подмешивая подсказки в prompt агента. Выбор такого комплекта не отменяет подготовленный официальный пример.

Скачанный `primer_iz_sbornika.dt` может быть связан с данным разделом книги, но это пока **гипотеза**: название файла и общая тема не доказывают совпадение содержимого. Нужны выгрузка, сравнение объектов/поведения и прогон формальных сценариев. Даже полное авторское решение нельзя считать истинным оракулом всех крайних случаев без такой проверки.
